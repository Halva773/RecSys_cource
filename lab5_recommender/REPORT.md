## Задание 1. Архитектура БД

### Сущности и таблицы

| Таблица        | Назначение                               | Ключевые поля                  |
|----------------|------------------------------------------|--------------------------------|
| `users`        | Пользователи, выставлявшие оценки и теги | `user_id` PK                   |
| `movies`       | Фильмы                                   | `movie_id` PK, `title`, `year` |
| `genres`       | Справочник жанров                        | `genre_id` PK, `name` UNIQUE   |
| `movie_genres` | Связь M:N фильм—жанр                     | (`movie_id`, `genre_id`) PK    |
| `ratings`      | Оценки пользователей фильмам (0.5–5.0)   | (`user_id`, `movie_id`) PK     |
| `tags`         | Текстовые теги пользователей к фильмам   | `user_id`, `movie_id`, `tag`   |
| `links`        | Внешние ID (IMDB / TMDB) для интеграций  | `movie_id` PK                  |

```

                  │movie_id│─────────│ movie_id      │──────────│ genres │
                  │ title  │         │ genre_id      │          │genre_id│

                  └───┬────┘                                    └────────┘

                  │ links  │

                  │tmdb_id │
```

### Обоснование структуры

- **3-я нормальная форма для жанров.** Жанр у фильма — атрибут типа M:N. Хранение как `genres TEXT` (через `|`) встречается в исходном CSV, но затрудняет фильтрацию и индексацию. Нормализация через `genres` + `movie_genres` даёт быстрый поиск «все боевики», нет дублирования значений жанра, и в ETL легко проверить целостность.
- **Композитный PK на `ratings`.** Пара (user, movie) уникальна — пользователь не может оценить один фильм дважды.
- **`links` отделён от `movies`.** Внешние ID нужны не всегда (например, для трейлеров с TMDB) и могут отсутствовать (`tmdb_id NULL`). Отдельная таблица сохраняет основную сущность чистой.
- **Индексы на `ratings(movie_id)` и `ratings(user_id)`** — рекомендатель регулярно ищет по пользователю (история) и по фильму (соседи).
- **SQLite выбран как СУБД** — нулевая настройка, файл в репозитории, легко защищать студентам. Та же схема дословно переносится на PostgreSQL/MySQL (только `INTEGER PRIMARY KEY AUTOINCREMENT` → `SERIAL`).

## Задание 3. Рекомендательные системы

Файл `recommender.py`. Все три класса работают поверх SQLite, никаких сетевых вызовов.

### 3.1 Content-Based Filtering (`ContentRecommender`)

- Признак каждого фильма — строка вида `"Action Comedy <теги пользователей>"`, переведённая в TF-IDF.
- **Похожие фильмы:** косинусная мера между TF-IDF строки выбранного фильма и всех остальных.
- **Рекомендации пользователю:** профиль = взвешенная сумма TF-IDF-векторов оценённых фильмов (с центрированием оценок при разнообразных оценках). Топ по cos-сходству, исключая уже виденное.

### 3.2 Collaborative Filtering (`CollaborativeRecommender`, item-based KNN)

- Матрица «фильмы × пользователи» по `ratings`. Удаляются фильмы с < 5 оценок (шумные).
- Центрирование по фильму убирает bias популярности (популярные фильмы средне получают высокие оценки, что искажает «похожесть»).
- Похожесть фильмов — `cosine_similarity` всей матрицы. На пользователе ранжируем кандидатов по `Σ sim(i, j) · (rating_j − 2.5)` — сдвиг даёт штраф низким оценкам и не вырождается, когда все оценки одинаковы.

### 3.3 Гибрид (`HybridRecommender`)

- Линейная комбинация `alpha · content + (1 − alpha) · collaborative` после min-max нормализации скоров обоих подходов в `[0, 1]` (иначе шкалы несравнимы).
- В UI ползунок `alpha` позволяет защищающемуся показать, как меняется выдача.
- Гибрид выигрывает при «тёплом» пользователе с разнообразной историей: collaborative даёт неожиданные хиты, content страхует от полностью нерелевантных рекомендаций.

## Задание 5. Холодный старт — текстовый ответ для устной защиты

> Этот раздел можно зачитать на защите.

**Что такое проблема холодного старта.** Рекомендательная система использует данные о взаимодействиях пользователей с объектами (оценки, клики, просмотры). Когда таких данных нет, система не может ранжировать. Различают три случая:

1. **Холодный пользователь** — новый user, у которого нет ни одной оценки. Collaborative filtering не работает: матрица «пользователь × фильм» пуста по соответствующей строке.
2. **Холодный объект** — новый фильм, который никто ещё не оценил. Снова collaborative не может предсказать рейтинг (нет столбца).
3. **Холодная система** — стартап без пользователей и без объектов одновременно (наш случай в полном объёме на этапе MVP).

**Какие проблемы это создаёт.** Качество выдачи на первых шагах определяет, останется ли пользователь в продукте. Если он впервые увидит шумные или нерелевантные рекомендации, он уходит. Бизнес-метрики (retention, CTR) деградируют. Это особенно остро для контентных площадок (Netflix, Spotify), где первая сессия — критическая.

**Подходы к решению, которые рассмотрены в работе:**

1. **Демографические / категориальные данные.** При регистрации спросить пол, возраст, страну. Затем рекомендовать на основе предпочтений похожей по демографии когорты. В нашем датасете демографии нет, поэтому этот путь только описан, не реализован.

2. **Атрибуты объекта (content-based как fallback).** Для нового фильма у нас всегда есть жанры и теги. Можно рекомендовать его пользователям, чьи прошлые любимые фильмы имеют близкий TF-IDF профиль. Это решает «холодный объект». В работе этот механизм встроен в `ContentRecommender` — он не требует ни одной оценки фильма.

3. **Активный сбор данных при онбординге.** Самый практичный вариант для холодного пользователя: показать ему набор популярных фильмов и попросить выбрать любимые жанры/фильмы. Так делает Netflix («Pick three movies you love»). Я реализовал упрощённую версию: на вкладке «Холодный старт» пользователь выбирает любимые жанры, и система выдаёт топ-N фильмов, у которых:
   - есть пересечение по жанрам с выбранными;
   - выше Bayesian-усреднённый рейтинг: `(n · mean + m · C) / (n + m)`, где `n` — число оценок фильма, `mean` — его средний рейтинг, `C` — глобальное среднее, `m` — порог уверенности (по умолчанию 30). Это страхует от ситуации «один фанат поставил 5.0».
   - дополнительный множитель `match_count / |chosen_genres|` повышает фильмы, попадающие во все выбранные жанры одновременно.

**Метрики.** Precision/Recall/F1 для top-N — наиболее понятные и стандартные метрики для рекомендательных систем при бинарной разметке релевантности. Их недостаток — не учитывают порядок внутри топа; более продвинутая метрика — NDCG@N, но для устной защиты P@N / R@N / F1@N достаточно прозрачны.

## Оценка моделей (leave-last-K-out)

`evaluate_models()` в `recommender.py`:

1. Берём 100 случайных пользователей с ≥ 30 оценок.
2. Сортируем их оценки по `timestamp`, последние **K** прячем как тест, остальные — train.
3. **Collaborative-модель переобучается на train** (без тестовых оценок) — это исключает leakage.
4. Релевант: фильм из теста с rating ≥ 4.
5. Считаем Precision@N, Recall@N, F1@N.

Результаты (100 пользователей, K = 10, top-N = 10, alpha = 0.5):

| Модель        | Precision | Recall    | F1        |
|---------------|-----------|-----------|-----------|
| Content       | 0.001     | 0.001     | 0.001     |
| Collaborative | **0.016** | **0.029** | **0.020** |
| Hybrid        | 0.008     | 0.012     | 0.009     |

При top-N = 20:

| Модель        | Precision | Recall    | F1        |
|---------------|-----------|-----------|-----------|
| Content       | 0.001     | 0.006     | 0.002     |
| Collaborative | **0.016** | **0.052** | **0.023** |
| Hybrid        | 0.007     | 0.028     | 0.011     |

**Что мы видим.**

- **Collaborative уверенно выигрывает.** На 9 742 фильмах попасть в 10 «правильных» из последних оценок крайне сложно, и абсолютные значения P@10 ≈ 0.016 — типичный порядок для item-based KNN на MovieLens.
- **Content слабее.** Он рекомендует «семантически близкие» фильмы по жанрам и тегам, но реальные предпочтения пользователя часто пересекают жанры (фанат боевиков смотрит и драмы) — TF-IDF этого не ловит.
- **Hybrid с alpha=0.5 не выигрывает у collaborative.** Это закономерное наблюдение для подобных датасетов: если одна из моделей сильно слабее, линейная комбинация её «разбавляет». На защите это хорошо обсуждается: оптимальный `alpha` нужно подбирать (cross-validation), и для MovieLens-подобных данных он смещён к 0 (близко к чистому collaborative). UI это позволяет показать живьём ползунком.

Абсолютные числа невысокие — это нормально для top-N evaluation при 9 742 кандидатах. Главное — правильная **относительная** картина: collaborative > hybrid > content.
